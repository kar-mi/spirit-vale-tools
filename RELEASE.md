# Releases

This repository has two independent release paths:

- reusable Bun packages are versioned with Changesets and published to GitHub
  Packages;
- the Windows portable UI application is built and released from a Git tag.

## Package releases

The publishable packages use the `@kar-mi` scope. Packages marked `private`
are workspace-only and are never published.

### 1. Add a Changeset

For every user-facing package change, create a Changeset and select the
affected publishable packages and their appropriate semver bump:

```powershell
bunx changeset
```

Commit the generated file under `.changeset/` with the implementation change.
Changesets updates dependent package ranges as needed when packages are
versioned.

### 2. Merge the change to `main`

The **Version and Publish Packages** workflow runs on every push to `main`.
It installs dependencies, type-checks, and runs the test suite.

When pending Changesets exist, the workflow creates or updates a version pull
request. That pull request contains the package version bumps, dependency
range updates, and changelog updates generated by Changesets.

### 3. Merge the version pull request

After the version pull request is merged, the same workflow runs again and
publishes the versioned, non-private `@kar-mi/spirit-vale-tools-*` packages to
GitHub Packages. The workflow uses the repository GitHub token for registry
authentication.

Consumers must configure the package scope before installing a package:

```ini
@kar-mi:registry=https://npm.pkg.github.com
```

### Package publish prerequisite

Publishable packages only include their `dist/` output and README. Build that
output before running `changeset publish`:

```powershell
bun run build:packages
bun run release:packages
```

The GitHub package workflow must likewise run `bun run build:packages` before
its publish step. Without that build, a clean runner has no `dist/` output to
publish.

## Windows portable UI release

The desktop application is not released by the package workflow. Its version
comes from the root `package.json` and its release workflow is triggered by an
`app-vX.Y.Z` tag.

1. Update the root application version in `package.json`.
2. Commit and merge the release commit to `main`.
3. Create and push a tag matching that version exactly:

   ```powershell
   git tag app-vX.Y.Z
   git push origin app-vX.Y.Z
   ```

4. The **Build and Release** workflow validates that the tag matches the root
   package version, type-checks and tests the repository, builds the portable
   ZIP, verifies it, and creates a GitHub Release with the ZIP and SHA-256
   checksum attached.

Use the workflow's manual-dispatch option to produce a seven-day dry-run
artifact without creating a GitHub Release.

## Quick reference

| Deliverable | Trigger | Version source | Destination |
| --- | --- | --- | --- |
| Reusable packages | Merge the Changesets version PR | Each package `package.json` | GitHub Packages |
| Windows portable UI | Push `app-vX.Y.Z` | Root `package.json` | GitHub Release |
